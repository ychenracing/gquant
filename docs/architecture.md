# 架构与代码结构

## 分工与依赖

```text
命令行 cli
  └─ application：校验、运行、账户续接、报告与验收编排
       ├─ engine：按交易日推进账户与风险状态
       ├─ operations：人工账户接管、状态恢复与实际成交对账
       ├─ strategy：收盘选股、目标权重、次日订单
       ├─ execution：开盘/独立预置保护的模拟成交与人工成交核对
       ├─ portfolio：持仓、可卖数量、现金、订单与独立会计规则
       ├─ risk：市场状态、组合回撤、个股退出
       ├─ market：行情宽表、因果指标、逐条行情校验
       ├─ research：绩效、固定参考、连续区间、账本与稳健性诊断
       └─ infrastructure：配置/行情读取、网络请求、身份和事务发布
```

领域模块不访问命令行、网络或输出目录。研究模块读取已经形成的账本，不复制选股与成交逻辑。依赖方向、循环依赖、模块长度和函数长度由仓库检查固定。

| `src/gquant/application/engine.py` | 会话顺序、模拟账户推进与可恢复状态 |
| `src/gquant/application/state.py` | 完整账户/风险/订单状态的JSON往返 |

## 单个交易日的数据流

1. 将隔夜持仓标记为可卖，并冻结隔夜组合供预置保护使用。
2. 用当日开盘价处理前一收盘生成的订单；容量只用此前已知成交量。当日最终成交量只作为回放中的“该日是否可成交”否决事实，不能参与开盘定仓。
3. 对前一收盘已武装的持仓逐只检查独立保护价。某只股票先退出不能取消另一只已经武装的保护。
4. 按收盘价估值；缺价持仓只使用最近有效价格作估值，不创造成交。
5. 更新市场状态、组合回撤、高水位、冷却和脉冲状态，形成下一可交易日订单。
6. 保存权益、敞口、市场状态、事件以及所有继续运行所需的状态。

完整退出意图优先于部分风险减仓。同一股票不能因为先生成了一张部分卖单，就延后已经明确的轮动完整退出。

## 连续状态和人工账户

`EngineState`保存继续同一账户路径所需的全部状态：现金、持仓、可卖数量、待执行订单、市场状态机、组合风险高水位/冷却、策略计数、已知价格/成交量，以及完整权益/敞口/状态历史。测试要求在任意支持的收盘点保存、JSON序列化并恢复后，与一次性完整回放的逐日权益、敞口、状态、事件和成交一致。

人工真实账户没有此前的模拟风险历史，因此首次接管必须显式`--risk-reset`。这个边界记录在状态中。收盘后除普通`pending_orders`外，还保存使用当时已知收盘信息决定的`conditional_orders`；次日实际成交可以由普通计划或这些预置条件保护授权，但系统不会用日线最低价替代真实券商回报。券商实际成交、人工主动偏差、外部入出金、拆送和净现金分红分别作为显式事件应用。普通计划与实际成交的偏差、人工覆盖和现金流均留在核对记录中。

账户同时保存真实账户权益与现金流中性的绩效权益。前者用于真实资金和次日定仓，后者用于收益、回撤高水位、波动率目标和脉冲控制，避免入金被算作策略收益或出金被算作策略亏损。每次账户发布还可独立追加到前向观察日志，日志只接受日期前进或完全相同状态的幂等重放。

该能力仍是人工决策支持：没有券商连接、订单发送、自动下单或后台交易任务。

## 数据与输出边界

应用入口校验整个冻结快照的文件集合、SHA256、行数、日期元数据、有限OHLCV和请求窗口覆盖范围。重复日期、空日期、哈希不符或请求结束日晚于快照都会拒绝运行，不做静默修补。

新获取数据先写入独立候选快照，完整校验后再发布；不会逐文件覆盖当前冻结数据形成混合代次。报告与账户状态也采用“完整目录 + 哈希清单 + 原子指针”发布，并用目录锁保证单写者。

项目保持单用户、单经济账户边界，不引入微服务、消息队列、多租户或自动交易基础设施。
